# BECONIC 기업 재무진단 · Claude Code 개발 마스터 프롬프트

버전: v1.0 / 작성: 2026-10-19 / 활용: Claude Code 프로젝트 루트에 이 파일을 복사하고 전체를 개발 요구사항으로 제공

> 목적: 기업대표와 컨설턴트가 **국세청 표준재무제표증명 등 3개년 실제 재무서류**를 기반으로 검증 가능한 재무비율·현금흐름 징후·실행과제를 확인하는 기업 재무진단 웹앱 제작.
>
> 기존 제공 파일 `BECONIC_Financial_Diagnosis_POC_v0.1.html`과 배포 예제의 `index.html`은 **기능 검증 시제품**이다. PDF/XLSX 자동 파싱, 공식 신용정보 연동, 완전한 은행 원장 분석은 미구현이므로 개발과 검증을 추가해야 한다. 시제품 값을 추정 또는 검증된 자료로 오인시키지 마라.

## 0. 역할 및 최상위 비타협 원칙

당신은 한국 중소기업회계와 재무분석을 이해하는 회계 전문가, 기업 신용위험 분석가, 풀스택 엔지니어, 정보보호 담당자, 문서 파서 개발자, 서비스디자이너, 접근성 담당자, 레드팀 QA 책임자로 동시에 작업한다.

- 실제 증빙이 없는 수치·비율·위험확률·기업신용등급·감사의견·산업 평균은 절대 생성하지 않는다.
- **계산은 결정론적 자바스크립트/TypeScript 코드**, Claude는 원인 검토 질문과 전략적 설명만 작성. Claude가 숫자를 고치거나 만들면 응답 폐기.
- **재무비율 ≠ 공인 기업신용평가등급**. 공식 등급은 적법하게 확보한 외부 평가기관의 유효한 평가서/정식 API가 있을 때만 원문 그대로 표시하며 평가기관·평가기준일·유효기간·등급체계를 함께 표시한다. 자체 진단점수는 공인 신용등급처럼 묘사하지 않는다.
- 원본 문서가 오타/OCR/분류 오류나 연도·단위가 불명확하면 사용자 확인 플래그로 격리한다. 확인 전 AI 분석 금지.
- 단일 HTML 정책: **사용자에게 제공하는 화면은 index.html 하나**. 정적 이미지/OG 파일 등은 필요에 따라 보조파일을 허용한다. API 키 보호 및 요청 검증용 Netlify Function 등 **별도 서버 측 코드가 불가피**하며, 이 기능을 브라우저에 넣지 않는다.
- 민감한 자료(사업자번호, 예금주, 계좌번호, 거래상대방, 거래적요 등)는 클라이언트 원칙 처리. API에는 **명시적 동의 후 필요한 집계수치**만 최소 전송하고 처리 안내를 제공한다. 계좌내역 전체를 Claude에 전송하는 것이 기본값이어서는 안 된다.
- 서버리스 API가 공개되어 무단 호출될 위험이 있다. 운영 버전에서는 승인된 호출자 인증, 사용량 제한, 남용 감시 및 예산 상한을 반드시 구현할 것. 서버리스 동일 출처 검사만으로 인증을 대체하지 말 것.
- 다른 사의 보고서 양식·저작물을 무단 복제하지 말고 공시된 기능에서 추상화한 독창적 UX와 설명을 만든다.

## 1. 사전 작업 및 결과물

1. 기존 `index.html`과 첨부 이미지, 방패형 로고의 실제 시각 요소를 검사한다. 현재 원본 Illustrator의 1페이지에서 방패 심볼을 추출해 시제품에 삽입하였으므로 임의 형태로 교체하지 말 것.
2. 요구사항을 `REQUIREMENTS.md`, 실제 개발 이력을 `CHANGELOG.md`, 테스트 결과를 `QA_REPORT.md`, 개인정보 처리 검토를 `PRIVACY_NOTES.md`에 정리한다.
3. 화면 1개 `index.html` 안에 CSS/JS 인라인 포함. 외부 CDN 의존성을 줄이고, 필요 시 사용한 OSS의 라이선스·SRI·버전을 관리.
4. 파싱 라이브러리를 쓰는 경우 빌드 단계에서 검증하고 최종 배포 폴더에 정적 파일로 번들할 수 있다. 소스 분리와 단일 HTML 산출을 구분하라.
5. `netlify/functions/finance-insights.mjs` 또는 대응되는 서버리스 함수에 API 키·모델 설정·입력 검증·서버 보호 적용. `ANTHROPIC_API_KEY`를 HTML 소스, 소스맵, 네트워크 응답, 로그에 절대로 넣지 않는다.
6. `og-finance.png`를 배포하고 실제 Netlify 공개 주소가 확정된 후 `og:image`에 **절대 HTTPS URL** 반영. 메타 title과 OG title은 서로 다른 메시지를 쓴다.
7. 최종 `index.html`, `netlify.toml`, 필요한 함수와 이미지, 테스트·설명 문서, 체크리스트 제공.

## 2. 타깃 사용자 및 사용 흐름

### A. 대표자 모드 (기본)
- 법인명, 업종, 개별/별도/연결, 결산월, 재무제표 회계기준, 자료 연도 3개 입력.
- **3개년 파일 업로드 → 추출 → 확인/보정 → 계산 → 대시보드 → 원인 점검 질문 → 우선과제 → PDF**.
- 화면 상단에 반드시 '우리 회사의 재무 현황', '주의할 지표', '원인을 확인할 자료', '지금 할 일'을 먼저 제시한다.
- 약어는 첫 회 원어가 아닌 쉬운 한국어 표기를 우선, 툴팁에서 용어·산식·해석·주의사항 제공.

### B. 컨설턴트 모드 (선택)
- 파일 출처와 업로드 시각, 재무제표의 표시단위, 개별·별도·연결 구분, 감사의견 출처, 공식 기업신용평가 보고서 발급기관/기준일/유효기간 관리.
- 재무 항목의 사용자 보정 및 수정 기록 비교, 저신뢰 데이터의 수동 승인, 검증표 다운로드.
- 위험별 증빙 서류 요청·현황·원인 확인 질문·담당자·일정을 관리하는 진단 보조 인터페이스.
- 외부 저장소 없이 운영 시 새로고침 후 자동복구를 약속하지 않는다. 동의 기반 로컬 저장 기능을 마련한다면 삭제와 저장범위, 공용PC 위험을 명시하고 암호화 정책 검토.

## 4. 원본 추출 정규화 스키마

- `organization`: legalName, businessIdentifier(masked), fiscalYearEnd, industryCode, financialStatementBasis(개별/별도/연결), accountingStandard, currency(KRW), uploaderConfirmation.
- `source`: documentId(local UUID), fileName, SHA-256, MIME, page, extractorVersion, extractedAt, docDate, fileSize, reportedUnit(원/천원/백만원), reviewStatus, sourceKind.
- `statement`: year, periodStart, periodEnd, classification, **원 단위 원본 정수/Decimal 문자열**, currency, provenance.
- `lineItem`: canonicalCode, originalLabel, value, sourcePage, sourceExcerpt, confidence, verifiedByUser, editedReason.
- `metric`: key, year, value|null, format(%/배/원), numerator, denominator, formulaId, sourceLineIds, eligibility, condition, referenceDate.
- `issue`: findingId, evidenceMetricIds, fact, significance, missingEvidence, riskCategory, priorityRule, userVerified, assessmentScope.
- `recommendation`: issueIds, action, evidence, timeframe, responsibleRole, KPIBase, KPITarget(nullable), KPIFormula, verificationData, caution.

P0 핵심 계정과목: `assets, currentAssets, noncurrentAssets, cash, tradeReceivables, inventory, liabilities, currentLiabilities, noncurrentLiabilities, shortTermBorrowings, longTermBorrowings, equity, paidInCapital, retainedEarnings, revenue, costOfSales, grossProfit, sga, operatingIncome, interestExpense, netIncome, tradePayables`.
P1: EBITDA를 계산할 때 감가상각비/무형자산상각비 **필요한 수치가 있는 경우에만**, 조정 EBITDA와 구분; ROA, ROE, 자산·매출채권 회전율, 재고 회전율, 매출채권 회수일수, 순차입금, 이자보상배율, 부채차입 관련 지표.

- 회사별 항목 명칭이 다른 경우 정규화 매핑 테이블 사용. 서로 다른 계정과목을 근거 없이 더하거나 대체하지 않는다.
- **같은 회사의 3개년, 같은 재무제표 기준, 같은 통화, 회계연도의 비교가능성** 우선 확인. 중간 결산, 분할·합병, 회계정책 변경, 재작성 자료는 비교제한 표시.
- **금액 단위**를 원본에 기록하고 정확히 원으로 변환 후 계산한다. 손익계산서와 재무상태표에 혼합단위가 있으면 검증 실패.
- 대차 검증: `자산총계 = 부채총계 + 자본총계`. 합계 누락, 반올림, 세목중복 가능성은 사용자 확인.
- 손익검증: 가능할 경우 `매출액 - 매출원가 = 매출총이익`, `매출총이익 - 판매비와관리비 = 영업이익`과 보고서 정의 검증.
- 원본 파일의 보안·문서 접근제한을 우회하지 않음; 깨진 서식은 수동 입력 요청.

## 5. 지표 공식: 확정계산과 예외처리 (P0~P1)

### P0 정량지표

| 표시명 | 계산식 | 비고 |
|---|---|---|
| 매출액 증가율 | (당기 매출 - 전기 매출) / 전기 매출 ×100 | 전기 매출이 0 이하이면 표시 보류 및 별도 해석 |
| 영업이익률 | 영업이익 / 매출액 ×100 | 분모 0이면 산출불가 |
| 순이익률 | 당기순이익 / 매출액 ×100 | 손실 시 음수 허용 |
| 매출총이익률 | 매출총이익 / 매출액 ×100 | 매출총이익 입력 확인 필수 |
| 부채비율 | 부채총계 / 자본총계 ×100 | 자본총계가 0 이하이면 **음의 부채비율을 정상 값처럼 출력 금지** |
| 자기자본비율 | 자본총계 / 자산총계 ×100 | 자본총계 음수는 그대로 위험 설명 |
| 유동비율 | 유동자산 / 유동부채 ×100 | 양수 분모 필요; 0은 산출불가/별도 상태 |
| 당좌비율 | (유동자산 - 재고자산) / 유동부채 ×100 | 재고자산·회계기준 정의 확인 필요; 단순 간이산식 표기 |
| 총차입금 | 단기차입금 + 장기차입금 등 범위가 확인된 금융부채 | 일반 부채총계와 구분 |
| 이자보상배율 | 영업이익 / 이자비용 | '배'로 표시, 이자비용 0이면 산출불가 |
| 자본잠식률 | (자본금 - 자본총계) / 자본금 ×100 | 자본금>0일 때, 양수일 때만 잠식률로 제시; 기업 형태 예외 주의 |
| 유동운전자본 | 유동자산 - 유동부채 | '백만원' 또는 '원', % 아님 |

### P1 심화지표

- 총자산회전율 = 당기 매출 / (기초·기말 총자산 평균). 첫 해 기초값이 없으면 '미산출'.
- ROA(총자산순이익률) = 순이익 / 평균 총자산 ×100. 선택 회계정의 명시.
- ROE(자기자본순이익률) = 순이익 / 평균 자기자본 ×100. 평균 자기자본 0 이하일 때 별도 해석.
- 매출채권회수기간 = 평균 매출채권 / 매출액 ×365 (회전 정의가 맞을 때). VAT 포함 여부, 매출기간 365/366 선택을 통일.
- 재고자산회전기간 = 평균 재고자산 / 매출원가 ×365. 재고자산 없거나 서비스업 등 관련성 낮으면 숨김.
- 현금전환주기 = 재고기간 + 매출채권회수기간 - 매입채무지급기간. 동기간·동정의 기준 확보 시에만.
- 영업현금흐름, 자유현금흐름은 **현금흐름표가 있거나 매입·매출 채권 등 충분한 원장정보가 있는 경우에만** 표시. 통장 입출금 차액을 영업현금흐름으로 쓰지 말 것.

### 임계값 규정

- 공식·학술·금융기관의 업종별 평균과 분포가 없는 경우 임의로 '위험 60점', '부채비율 200% 이상 불량' 같은 상수 채택 금지.
- `유동자산 < 유동부채`, `자본총계 <= 0`, `영업이익 < 0`, `자산 != 부채+자본`처럼 **수치의 정의에 직접 근거한 징후**는 표시 가능하되 실제 지급불능/부도 확정 표현 금지.
- 추후 사용자가 업종별 벤치마크 파일 또는 사용 허가된 공식 데이터 연동 시 `기준값·자료원·표본·연도·집계방법`과 함께 표시.
- 급격한 전년 대비 변화는 퍼센트포인트(p.p.)와 상대증감(%)을 구별할 것. 연속 3년 차트에서는 3개 연도 값과 기간 표시.

## 6. 은행계좌 기반 실현금흐름 모듈

- 사용자는 개별 계좌별로 CSV/XLSX를 업로드하고 은행명, 계좌별 식별 별칭, 거래기간, 원본 화폐 단위와 기간완전성을 확인.
- 필수 원장: 거래일자/시간, 거래금액, 입금/출금 구분, 잔액, 원래 거래 텍스트(개인정보 최소화), 계좌 식별(내부 별칭).
- **중복**: 계좌별 동일 거래·일시·금액·잔액 조합 등 후보 식별. 동일 금액의 정상 거래를 자동 삭제 금지.
- **계좌 간 이체**: 한 회사의 계좌 간 양측 거래 매칭 후보를 표시하여 합산시 중복 자금유입으로 왜곡되지 않게 함. 확정 시 사용자 승인.
- **거래 범주**: 고객수금/매입대금/인건비/세금/금융차입/차입상환/투자유치/내부이체/미분류. 자동분류는 정확도·사용자승인·근거를 기록.
- 계좌잔액 검증: 기초잔액 + 총입금 - 총출금 = 기말잔액(동기간/동계좌인 경우). 일자 누락·필터·은행 엑셀 수식 주의.
- 실제 조회 계좌가 일부일 경우 '전체 회사 현금흐름'이 아닌 **'제출된 계좌의 순입출금'**으로 표현.
- 현금흐름 전망 기능은 P2 선택사항. 예상 매출/수금일/지출 계획 가정을 사용자로부터 별도 입력 받아 시나리오로 표시하고 예측치에 '가정' 라벨.

## 7. 공식 신용등급·감사의견 정보 모듈

- `creditAgency, rating, ratingScale, issuedAt, validTo, basisReport`를 별도 입력/첨부 또는 합법적 API 연동.
- 등급이 없으면 **'미확인'**으로 표시. 공식 기관별 체계가 다를 수 있으므로 임의 등급 매핑 금지.
- 감사의견은 적정/한정/부적정/의견거절/비대상/미확인. 외부감사 미대상과 의견거절을 구별.
- 감사의견은 영업실적/신용위험 보증 아님. 강조사항·계속기업 관련 중요한 불확실성, 감사인의 의견 근거가 있다면 별도 설명.
- 회계감사보고서는 금융감독원 전자공시 등 공개된 공식자료의 실제 링크/문서와 연결하되 공개범위와 제공권한 확인.
- 신용평가사 API는 계약·이용허락이 필요할 수 있으므로 무단 크롤링을 금지한다.

## 8. 사용자 화면 설계 (실제 레이아웃)

`헤더(로고/진단명/데이터보호) → 1. 회사 정보 → 2. 서류 업로드 → 3. 추출·검증 → 4. 재무 대시보드 → 5. 세부 분석 → 6. 위험과 근거 → 7. AI 개선처방 → 8. 12개월 로드맵 → 9. PDF`.

대시보드에서 **맨 위 4개 카드**: 매출액(백만원), 영업이익률(%), 부채비율(%), 유동비율(%). 아래에 자기자본비율, 순이익률, 자본잠식 확인, 이자보상배율, 단기상환 예정액(입력 자료 있을 때만). 모든 카드는 `정보ⓘ → 공식 → 입력 연도 → 값 → 해석 주의` 지원.

시각화 우선순위:
1. 매출/영업이익/순이익 3개년 비교(혼합 단위의 이중축 사용을 지양).
2. 재무상태표 구성(자산 = 부채+자본) 3개년 누적 막대(음의 자본 처리 별도).
3. 유동비율·부채비율·자기자본비율 선형 변화(축의 오해 방지).
4. 입력된 계좌별 월별 총입금/총출금/순입출금(기간 12개월 미만 시 안내).
5. 중요위험 3개 이내 우선 요약 + 나머지 상세 접기.
6. 레이더 차트는 검증된 표준화 기준값/분포가 없으면 사용하지 말 것. 서로 다른 비율을 임의 0~100점으로 환산하는 그래프 금지.

UX:
- 한국어 중심, 원어 병기 필요 시 툴팁에만 사용. `자본잠식`, `자기자본`, `당좌비율`, `이자보상배율`, `현금전환주기`를 실제 초보 경영자가 이해할 수 있도록 설명.
- PC/태블릿/모바일 대응, 터치영역 44px, 명확한 오류 문장, 키보드/스크린리더 접근성, 색상 이외 패턴으로 상태 구분.
- 3개년 입력 중 파일 누락·감사 미대상·계좌 일부 제출을 모두 **'정보 없음'**과 구분해 사용자에게 알릴 것.
- 사용자 안내: 세금계산서/재무제표증명만으로 현재일의 현금잔액을 확정할 수 없음을 표시.

## 9. AI 분석 — 검증 후 보조 작성

반드시 순서: `원본 추출 → 사용자 확인 → 계산 → 수치 검증 → 위험 룰 → Claude 자연어 초안 → 수치 대조 → 보고서 렌더링`.

- Anthropic 공식 Structured Outputs API(`output_config.format`)와 검증 스키마 활용을 우선 검토. 배포 모델이 구조화 출력을 지원하는지 확인.
- 요청에는 `수치/공식/확정된 근거 참조ID/출처연도/불명확한 사항`만 포함. 원본 PDF·거래내역 원문 기본 전송 금지.
- 출력 JSON 예: `executiveSummary, observations[{metricId,year,fact,impact,confidenceScope}], risks[{evidenceIds,risk,verifyNext}], actions[{priority,ownerRole,timeline,kpiFormula,neededData}], limitations[]`.
- AI 결과의 모든 수치와 단위가 원본 계산 엔진 결과와 일치하는지 검증; 차이 발생 시 블록 제외하고 표시.
- AI에 사실과 권고를 분리 지시: '확인된 사실', '추가 확인 필요', '권고사항'. 향후 매출·등급·상환능력 예측을 사실처럼 출력 금지.
- 응답 지연/쿼터/장애 시 기본 결정론적 분석 결과와 PDF 출력 가능해야 함.

## 10. 보고서 PDF 규격 (컨설팅펌 수준)

- A4 세로, 14~16mm 여백, 가독성 좋은 프리텐다드/한글 대체폰트, 테이블 줄바꿈 `word-break:keep-all`과 페이지 분리 통제.
- 서론 없이 바로 Executive Summary: 현재 상태 3문장, 가장 중요한 위험 최대 3개, 증빙의 범위와 신뢰도.
- 1쪽 표지/핵심요약, 2쪽 입력자료·검증 현황, 3~4쪽 성장·수익성, 5~6쪽 안정·유동성/자본잠식, 7쪽 통장 흐름(자료 있을 때), 8쪽 외부 신용등급/감사결과(확인된 때), 9~10쪽 원인·리스크, 11~12쪽 개선전략/우선과제, 13쪽 90일/12개월 로드맵, 14쪽 KPI/측정법, 15쪽 근거/공식·용어집·유의사항의 **가변 8~15쪽** 설계. 자료가 없으면 빈 페이지를 생성하지 않는다.
- 표 제목 반복, 금액과 분모의 부호 보존, 숫자 글자단위 세로분절 방지, 차트와 범례를 붙여 분리 방지, `thead { display: table-header-group }`, `tr { break-inside:avoid }`, 실제 인쇄 미리보기 확인.
- 모든 페이지에 기업명, 자료 기준 연도, 페이지번호, 그로스벤처스 방패 로고 및 보고서 기밀성 주석 (선택), **'공식 기업신용평가서 아님'** 을 적절하게 표시.
- 내보내기는 원칙적으로 브라우저 인쇄→PDF. 운영 고도화시 수집 동의·접근제어를 갖춘 전용 PDF 생성 서버를 고려하되 서버 로그 및 첨부 저장 점검.

## 13. QA·레드팀 필수 통과항목

테스트는 자가부검 2회 + 레드팀 공격 1회 + 실제 PDF 렌더링 확인 1회 이상 반복하고 결과를 `QA_REPORT.md`에 표로 기록.

- [ ] 파일을 올리지 않았을 때 매출/자산/점수에 어떤 숫자도 자동 표시되지 않음.
- [ ] 3개년 동일 기업/결산 기간/단위/개별·연결 기준 혼합시 경고 또는 차단.
- [ ] `자산 != 부채+자본`면 수치 확인을 요구하고 AI 분석 진입 차단.
- [ ] 자본총계가 0/음수면 부채비율을 단순 음수 퍼센트로 표현하지 않음.
- [ ] 매출액 0 또는 전기 매출 0일 때 증가율 산출/표현 오류가 없음.
- [ ] 상장법인·금융업·창업 초기·매출 없는 스타트업 사례에서 무의미 지표 자동 숨김.
- [ ] 금융 통장 입금 합계가 영업매출 또는 영업현금흐름으로 잘못 표현되지 않음.
- [ ] 은행 내부이체 A→B가 총유입으로 중복 카운트되지 않도록 분석 범위와 미분류 표시.
- [ ] 외부감사 미대상과 감사의견 의견거절을 구별.
- [ ] AI가 공식 신용등급, 부도확률, 가상 업종평균을 생성하면 차단.
- [ ] 원본 파일·사업자번호·계좌번호·거래상대방이 네트워크/로그로 의도치 않게 노출되지 않음.
- [ ] 브라우저 JS에서 `ANTHROPIC_API_KEY` 검색 결과 0건, 비밀키가 서버 함수에만 있음.
- [ ] 서버의 API를 무단 사용하지 못하도록 인증·요청 제한·예산 제어 추가(미완성이라면 운영 불가 판정).

- [ ] 실제 Netlify 배포 URL에서 OG 이미지 절대경로 확인 및 미리보기 테스트.
- [ ] 서버 응답 오류·AI 시간초과·부분 데이터·파일 손상·비대상 업종에도 안전한 실패 UX.

## 14. 개발 검수 보고서 출력 방식

최종 답변에서 다음 표 작성: `요구사항 | 구현 여부(완료/부분/미구현) | 사용자 확인 방법 | 남은 리스크 | 차기 대응`. 진행하지 않은 기능은 절대 완료로 적지 않는다. 테스트 통과 스크린샷과 실제 PDF 출력물에서 최소 3쪽 이상을 확인하며 미통과 항목을 명시한다. 파일 자동 파싱의 완성도와 공식 신용등급 연동의 계약/권한 여부를 특히 명확하게 구분한다.
